### 0.2 순서 변경에 따른 알려진 비용

원안은 Part A(공개/관리 표면 분리)를 Task 3보다 먼저 두는 것이었다. 순서가 바뀌면서
다음 비용이 발생하며, 이는 **예상된 것이지 결함이 아니다.**

- Task 3이 추가하는 관리자 라우트(test access grant 승인 UI 등)를 Part A에서
  `(admin)` route group으로 **한 번 더 이동**해야 한다.
- route group은 URL에 나타나지 않으므로 이 이동은 **파일 위치 변경일 뿐 URL·동작이
  바뀌지 않는다.** 기계적 작업이며 위험도는 낮다.

**완화 조치 — Task 3 수행 시 미리 지킬 것:**

1. 새 관리자 라우트는 기존 `apps/web/app/[locale]/admin/**` 아래에만 만든다.
   공개 경로에 관리 기능을 두지 않는다.
2. 새 라우트에서 절대 URL을 하드코딩하지 않는다. 기존 `admin-routing.ts`의
   경로 생성 헬퍼를 사용하거나 확장한다. Part A에서 이 헬퍼를 설정 모듈로
   승격시킬 예정이므로, 경로 생성이 한곳에 모여 있을수록 이동이 쉬워진다.
3. 새 라우트가 공개 layout이 아니라 관리자 layout을 사용하도록 한다.

### 0.3 여전히 유효한 문제 (Part A·C에서 해소)

순서를 미루더라도 아래 두 가지는 **현재 존재하는 결함**이며 그대로 남아 있다.
Task 3 진행 중 악화시키지 않도록 인지한다.

1. `proxy.ts`가 공개 랜딩과 QR 스캔 경로에서도 Supabase 인증을 갱신한다(2.1 참조).
   **Task 3에서 이 matcher를 더 넓히지 말 것.**
2. 차주 활성화 화면이 존재하지 않는 문서(`TERMS_V1`)에 대한 동의를 받아 DB에
   기록하고 있다(2.2 참조). **Task 3에서 새로운 동의 수집을 추가하지 말 것.**

## 1. 배경과 목표

### 1.1 제품 맥락

Taptolk는 B2B SaaS다. 실제 계약 주체는 관리회사이고, 방문자·차주는 계약사가 배포한
QR을 통해 유입되는 최종 사용자다. 그러나 현재 랜딩은 방문자 안내에 치우쳐 있고
**계약 이전 단계(도입 문의)가 존재하지 않는다.**

### 1.2 목표

1. 공개 표면과 관리 표면을 호스트 단위로 분리할 수 있는 구조를 만든다.
2. 계약하지 않은 관리회사가 도입을 문의할 경로를 만든다(이메일 + 문의 폼).
3. 이용약관·개인정보처리방침 문서와 페이지를 만들어 동의 기록에 실체를 부여한다.
4. 랜딩이 차주·관리회사 관점의 사용 흐름까지 설명하게 한다.

### 1.3 비목표 (이번 범위 아님)

- 실제 도메인 구매·연결 (사용자 승인 대기)
- 요금제·가격 공개
- CAPTCHA Provider 도입 (미결정)
- 결제·계약 자동화

## 2. 확인된 현재 상태 (코드 근거)

### 2.1 공개 경로가 인증에 결합돼 있음

`apps/web/proxy.ts`의 matcher는 API·정적 자원만 제외한다.

```
matcher: ["/((?!api|_next/static|_next/image|brand|favicon.ico|robots.txt|sitemap.xml|.*\\..*).*)"]
```

`/ko`(랜딩), `/ko/q/[publicToken]`(QR 스캔), `/ko/c/[sessionToken]`(대기실),
`/ko/activate/*`, `/ko/owner`는 모두 이 패턴에 걸리며, 미들웨어는 이들 경로에서도
`client.auth.getClaims()`를 호출해 **Supabase 인증 세션을 갱신**한다.

결과:
- 영원히 로그인하지 않을 익명 방문자의 QR 스캔 경로에 Supabase Auth 왕복이 추가된다.
- 관리자가 같은 브라우저를 쓰면 관리자 인증 쿠키가 공개 요청에 동봉된다.
- 한 origin에 4종 세션이 공존한다: Supabase Auth(`sb-*`), `tt_owner_session`,
  `tt_caller_anon`+`tt_contact_session`, `taptolk_locale`.

### 2.2 존재하지 않는 문서에 동의를 받고 있음

- `apps/web/components/owner-activation-view.tsx:162` — `termsVersion: "TERMS_V1"`이
  **React 컴포넌트에 하드코딩**돼 있다. `AGENTS.md`의 "컴포넌트에 비즈니스 규칙·문구·
  URL을 하드코딩하지 않는다" 규칙 위반이기도 하다.
- `public.owners` 테이블은 `terms_version`, `privacy_version`, `consented_at`을
  `not null`로 기록한다. 즉 **버전 있는 법적 문서를 전제로 설계돼 있다.**
- 그러나 `/terms`, `/privacy` 라우트와 문서가 존재하지 않는다(라우트 검색 0건).
- 차주 동의 문구는 "이용약관과 개인정보 처리방침에 동의합니다"인데 링크가 없다.

### 2.3 도입 문의 경로 부재

`contact` / `inquiry` / `pricing` 관련 공개 라우트 0건. 랜딩의 관리회사 카드 CTA는
`고객 관리자 로그인` 하나뿐이며, 이는 이미 계정이 있는 사용자 전용이다.

### 2.4 보존·수집 정책 실측값 (법적 문서 초안의 사실 근거)

| 항목 | 실제 구현 |
|---|---|
| 차주 전화번호 | `phone_hash`(고유) + `phone_ciphertext` + `phone_key_version` + `phone_last4` |
| 차량번호 | `plate_lookup_hash`(SHA-256) + `plate_ciphertext`(AES-GCM) + `plate_last4` |
| 메시지 보존 | `MESSAGE_RETENTION_HOURS` 기본 **72시간** |
| 자유 입력 길이 | `FREE_MESSAGE_MAX_LENGTH` 기본 **200자** |
| OTP 제한 | 시도 5회 / 시간당 5회 / 일 10회 (전화번호 기준) |
| QR 요청 제한 | `IP_QR_LIMIT_PER_10_MINUTES` 기본 3회 |
| 로그 | 전화번호·메시지 본문·OTP·토큰 미기록(redaction 경계) |
| 관리자 | 이메일, 표시 이름, 역할·소속 범위, MFA 상태 |

## 3. Part A — 공개/관리 표면 분리 (승인 불필요 범위)

### 3.1 목적

실제 도메인 연결 없이, **호스트 분리가 가능한 코드 구조**를 만든다.
도메인 확정 시 설정 변경만으로 분리가 완료되어야 한다.

### 3.2 요구사항

**A-1. `proxy.ts`에서 공개 경로를 인증 대상에서 제외한다.**

- locale 판별·리다이렉트는 **모든 경로에서 유지**한다(공개 경로도 `/ko`·`/en` 필요).
- Supabase 세션 갱신(`createTaptolkServerClient` + `getClaims()`)은
  **관리 경로에서만** 수행한다.
- 관리 경로 판별은 하드코딩하지 말고 타입 있는 설정 모듈에서 가져온다.
- 공개 경로에서 Supabase 설정이 없어도 정상 동작해야 한다(현재도 fail-safe이나
  이번에 명시적으로 분리한다).

**A-2. 라우트를 공개/관리 route group으로 분리한다.**

```
apps/web/app/[locale]/
  (public)/          랜딩, onboarding, q, c, activate, respond, owner, terms, privacy, contact
  (admin)/           login, signup, dashboard, platform, sites, qr-inventory, operations, access, mfa
```

- URL 경로는 **변경하지 않는다.** route group은 URL에 나타나지 않으므로
  기존 URL(`/ko/admin/login` 등)과 인쇄물 URL(`/ko/q/...`)이 그대로 유지된다.
- 각 group에 별도 `layout.tsx`를 두어 공개/관리의 헤더·캐시 정책을 분리한다.
- 공개 group: 정적 우선, 인증 컨텍스트 없음.
- 관리 group: `no-store`, 인증 컨텍스트 필수.

**A-3. 호스트 경계를 타입 있는 설정으로 표현한다.**

- `packages/config`에 공개 URL 기준(base URL)과 관리 URL 기준을 분리해 정의한다.
- 두 값이 같으면 현재처럼 단일 호스트로 동작하고, 다르면 호스트 분리로 동작한다.
- 크로스 호스트 링크(랜딩 → 관리자 로그인, 관리자 → 랜딩)는 이 설정에서 생성한다.
  **컴포넌트에 절대 URL을 하드코딩하지 않는다.**
- 기본값은 현재와 동일한 단일 호스트여야 한다. 이번 변경으로 **동작이 바뀌면 안 된다.**

**A-4. 서버 전용 경계를 유지한다.**

- 관리 경로 판별 로직과 URL 설정은 브라우저 번들에 secret을 노출하지 않는다.
- 공개 base URL은 `NEXT_PUBLIC_`으로 노출 가능하나, 관리 호스트 판별 로직 자체는
  서버에서 수행한다.

### 3.3 하지 말 것

- 실제 도메인·서브도메인을 코드나 설정에 확정 값으로 넣지 말 것 (사용자 승인 대기).
- Supabase Auth 쿠키 도메인 설정을 변경하지 말 것 (도메인 확정 후 별도 작업).
- 인증 시스템·계정 체계를 분리하지 말 것. **하나의 Supabase Auth, 하나의 로그인
  진입점**을 유지한다(Task 2 결과 보존).
- 기존 URL 경로를 변경하지 말 것.

### 3.4 수용 기준

- [ ] 공개 경로 요청에서 Supabase 인증 호출이 발생하지 않음을 테스트로 증명
- [ ] locale 판별·리다이렉트는 공개·관리 모두에서 기존과 동일하게 동작
- [ ] 기존 URL 전부 무변경 (특히 `/[locale]/q/[publicToken]`)
- [ ] 공개/관리 layout 분리, 관리 경로 `no-store`
- [ ] URL이 타입 있는 설정에서 생성됨, 컴포넌트 하드코딩 0
- [ ] 단일 호스트 기본값에서 기존 E2E 전부 PASS
- [ ] `corepack pnpm verify` PASS

## 4. Part C — 이용약관·개인정보처리방침 (Part B보다 먼저)

> **Part B(문의 폼)보다 먼저 수행한다.** 문의 폼은 개인정보를 수집하므로
> 처리방침이 선행되어야 한다.

### 4.1 요구사항

**C-1. 버전 있는 법적 문서 모듈을 만든다.**

- 문서 본문을 타입 있는 content 모듈로 관리한다(KO/EN 동시).
- 각 문서는 **버전 식별자와 시행일**을 가진다. 버전 형식은 기존 도메인 정책의
  정규식 `^[A-Z0-9][A-Z0-9._-]{0,31}$`을 따른다(`packages/domain/src/owner-activation-policy.ts:84`).
- 초기 버전: 약관 `TERMS_V1`, 처리방침 `PRIVACY_V1` (기존 하드코딩 값과 일치시켜
  이미 기록된 동의 데이터와 정합을 유지한다).

**C-2. 공개 페이지를 추가한다.**

- `/[locale]/terms`, `/[locale]/privacy`
- 공개 route group에 위치. 인증 불필요, 정적 렌더링.
- 문서 상단에 버전과 시행일을 표시한다.
- 목차(앵커 링크) 제공, 접근성 준수(SemanticHeading, 320px 무오버플로).

**C-3. 하드코딩된 동의 버전을 제거한다.**

- `apps/web/components/owner-activation-view.tsx:162`의 `termsVersion: "TERMS_V1"`과
  privacy 버전을 **설정/content 모듈에서 주입**받도록 변경한다.
- 차주 활성화 동의 문구에 **약관·처리방침 링크를 추가**한다(새 창 또는 같은 창 이동
  후 복귀 가능하게 하되, 입력 중이던 값이 유실되지 않도록 주의).

**C-4. footer에 법적 링크와 사업자 정보를 추가한다.**

- 공개 layout footer: 이용약관, 개인정보처리방침, 도입 문의, 사업자 정보.
- **사업자 정보(상호·대표자·사업자등록번호·주소·연락처)는 사용자가 제공해야 하는
  값이다.** 확정 전에는 content 모듈에 플레이스홀더 키만 만들고, 값이 비어 있으면
  해당 항목을 **렌더링하지 않는다**(가짜 값을 넣지 말 것).

### 4.2 문서 초안 — 이용약관·개인정보처리방침

> **문안 원본은 `docs/legal/terms-and-privacy-draft.md`로 이관되었다.**
> 중복 원본을 두지 않기 위해 PRD의 인라인 초안은 제거했다. 구현 시 반드시 해당 문서를
> 단일 원본으로 사용한다.

해당 문서가 포함하는 것:

- 이용약관 KO/EN 전문 (`TERMS_V1`, 10개 조항)
- 개인정보처리방침 KO/EN 전문 (`PRIVACY_V1`, 10개 항목)
- 버전을 `V1`로 유지해야 하는 이유(기록된 동의 데이터와의 정합)
- 값이 없으면 렌더링하지 않을 미확정 항목 목록
- 서비스 개시 전 법률 검토 시 확인할 쟁점 8건
- 구현 시 준수 사항

**법률 검토 상태(사용자 결정 2026-07-21): 서비스 개시 전 완료.** 그 전까지는 본 초안
문안으로 페이지를 구현하되, 검토 결과로 문안이 실질적으로 바뀌면 버전을 올린다.

### 4.4 수용 기준

- [ ] `/[locale]/terms`, `/[locale]/privacy` 공개 페이지, KO/EN 동시
- [ ] 문서 본문이 타입 있는 content 모듈에 위치, 컴포넌트 하드코딩 0
- [ ] 버전·시행일이 문서에 표시되고 정규식 계약을 만족
- [ ] `owner-activation-view.tsx`의 하드코딩된 버전 제거, 설정에서 주입
- [ ] 차주 동의 문구에 두 문서 링크 연결
- [ ] 미확정 항목(위탁·국외이전·보호책임자·사업자정보)은 값이 없으면 미렌더링
- [ ] footer 법적 링크, 320/768/1280/1920 확인
- [ ] `corepack pnpm validate:wcj` PASS, Axe 위반 0
- [ ] 기존 차주 활성화 E2E 회귀 없음

## 5. Part B — 도입 문의 (이메일 + 문의 폼)

### 5.1 사용자 결정 사항

**이메일 링크와 문의 폼 두 가지를 모두 제공한다** (2026-07-21 결정).

### 5.2 B-1. 이메일 경로

- 랜딩과 문의 페이지에 문의 이메일 주소를 노출한다.
- 이메일 주소는 content/설정 모듈에서 관리한다. **값이 확정되기 전에는 이메일
  경로를 렌더링하지 않는다.** 임의 주소를 만들어 넣지 말 것.

### 5.3 B-2. 문의 폼

**라우트:** `/[locale]/contact` (공개 route group)

**수집 항목**

| 필드 | 필수 | 비고 |
|---|---|---|
| 회사명 | 필수 | |
| 담당자명 | 필수 | |
| 이메일 | 필수 | 회신용 |
| 연락처 | 선택 | |
| 관리 단지 수 | 선택 | 구간 선택 |
| 관리 차량 대수 | 선택 | 구간 선택 |
| 문의 내용 | 필수 | 길이 상한을 정책 모듈에 정의 |
| 개인정보 수집·이용 동의 | 필수 | 처리방침 링크 필수 |

**아키텍처 요구사항**

- 계층을 반드시 지킨다:
  `UI → Route Handler → Application Service → Domain Policy → Repository → PostgreSQL`
- 신규 테이블(예: `contract_inquiries`)은 **tenant에 속하지 않는 플랫폼 범위**다.
  `tenant_id`를 두지 않는다.
- **RLS 필수.** 공개 사용자는 직접 insert할 수 없다. 서버 Route Handler를 경유한
  통제된 경로로만 기록한다. 조회·수정은 플랫폼 관리자 역할만 가능하다.
- **개인정보는 저장 시 암호화한다.** 기존 `owners`/`vehicles` 패턴
  (`apps/web/owner/owner-activation-crypto.ts`, ciphertext + lookup hash)을 따른다.
  복호화는 권한을 통과한 Application Service 경로에서만 가능하며 감사 기록을 남긴다.
- 동의 버전(`PRIVACY_V1`)과 동의 시각을 함께 기록한다.
- 처리 상태(접수/처리중/완료)와 처리자·처리 시각을 기록한다.
- 보안 관련 mutation은 **redacted audit을 같은 트랜잭션에** 기록한다.

**스팸·남용 방지 (CAPTCHA Provider 미결정 상태에서의 대응)**

CAPTCHA Provider는 사용자 미결정 항목이므로 **도입하지 않는다.** 대신:
- IP 기반 비가역 해시로 rate limit (기존 `IP_QR_LIMIT_PER_10_MINUTES` 패턴 참고,
  값은 정책 모듈에 별도 정의)
- honeypot 필드(사람에게 보이지 않고 채워지면 거부)
- 서버 측 최소 제출 소요시간 검증
- 상한 초과 시 **fail closed**. 조용히 통과시키지 않는다.
- CAPTCHA 자리는 Port 경계로 비워두되, Provider를 선택하거나 설정하지 말 것.

**금지 사항**
- 문의자 이메일·전화번호를 **로그, 오류 메시지, 감사 기록 본문에 남기지 말 것.**
- 자동 회신 메일을 발송하지 말 것 (SMS/메일 Provider 미결정).
- 문의 내용을 관리자 화면에 노출하는 기능은 **플랫폼 관리자 권한 + RLS 통과**
  경로로만 구현한다.

**상태·오류 설계**
- 로딩, 성공, 검증 실패, 한도 초과, 서버 불가 상태를 모두 KO/EN으로 설계한다.
- 성공 시 접수 안내와 예상 회신 경로를 안내한다(구체적 회신 기한은 약속하지 말 것).

### 5.4 B-3. 플랫폼 관리자 문의 목록 (필수 — 생략 불가)

**이 화면이 없으면 Part B 전체가 무의미하다.** 자동 회신 메일은 Provider 미결정으로
범위 밖이므로, 접수된 문의를 사람이 확인할 **유일한 경로가 이 화면**이다.
이것이 없으면 문의가 DB에만 쌓이고 아무도 보지 못한다.

**라우트:** 관리 route group 내 플랫폼 영역 (예: `/[locale]/admin/platform/inquiries`)

**요구사항**
- **플랫폼 관리자 역할만** 접근한다. 고객 관리자(관리회사·사이트)는 접근할 수 없다.
  중앙 RBAC와 RLS를 **모두** 통과해야 한다.
- 목록: 접수 일시, 회사명, 담당자명, 규모, 처리 상태. **연락처는 목록에 노출하지 않는다.**
- 상세: 문의 내용과 연락처를 확인한다. **복호화가 발생하는 조회는 감사 기록을 남긴다.**
- 처리 상태 변경(접수 → 처리중 → 완료)과 처리자·처리 시각 기록. 상태 변경은
  redacted audit을 같은 트랜잭션에 기록한다.
- 목록·상세·상태 변경 모두 로딩/빈 상태/권한 없음/오류 상태를 KO/EN으로 설계한다.
- **이 화면에서 문의자에게 직접 발송하는 기능을 만들지 않는다**(Provider 미결정).
  담당자가 자신의 메일 클라이언트로 회신하는 것을 전제로 한다.

**보존 처리**
- 접수일로부터 1년이 지난 문의를 삭제·비식별 처리하는 경로를 구현한다.
- **활성 Cron을 추가하지 않는다.** 기존 privacy cleanup과 동일하게 인증된 수동 실행
  경로로 두고, 실제 스케줄 활성화는 서비스 개시 승인 시점에 별도로 다룬다.
- 정리 실행 결과는 집계 값만 기록하고 개인정보를 남기지 않는다.

### 5.5 승인 필요 (Codex가 임의 결정 금지)

## 6. Part D — 랜딩 콘텐츠 보강

### 6.1 요구사항

**D-1. 사용 흐름을 3주체로 확장한다.**

현재 SCAN → SEND → REPLY 3단계는 방문자 여정만 설명한다. 다음을 추가한다.

- **차주 흐름**: QR 스티커 수령 → 본인확인 후 활성화 → 연락 도착 → 원터치 응답
- **관리회사 흐름**: 계약 → 사이트 등록 → QR 발급·승인 → 입고·배포·차량 배정 →
  운영 현황 확인

기존 방문자 3단계를 없애지 말고, 주체별로 구분해 보여준다.

**D-2. 관리회사 가치 제안 섹션을 추가한다.**

계약 결정권자가 얻는 것을 서술한다. 다음 근거는 실제 구현된 기능이다.
- 차주 전화번호 노출 없이 민원 연락을 처리
- QR 발급부터 교체·폐기까지 자산 이력 추적
- 미응답 시 관리사무소 에스컬레이션
- 반복·악의 연락 통제와 신고 처리
- 응답률·미해결·발송 비용 등 운영 지표

**구현되지 않은 기능을 가치로 서술하지 말 것.** 위 목록 밖의 효익을 추가하려면
실제 코드로 존재하는지 먼저 확인한다.

**D-3. 도입 문의 CTA를 배치한다.**

- 관리회사 카드의 CTA를 **`도입 문의`(주) + `고객 관리자 로그인`(부)** 2개로 분리한다.
  현재는 로그인 하나뿐이라 미계약 회사가 갈 곳이 없다.
- 히어로 또는 가치 제안 섹션 하단에도 도입 문의 진입점을 둔다.

**D-4. footer를 확장한다.**

- 이용약관 · 개인정보처리방침 · 도입 문의 · (확정 시) 사업자 정보
- 현재 슬로건 한 줄 구조를 대체한다.
