# 콘솔 계층 기획 — 관리회사 › 사이트 › QR (2026-07-23)

이 문서는 **기획 정리본**이다. 착수 전에 사용자 확정이 필요한 항목을 §7에 모았다.
화면 형태는 `DESIGN_SYSTEM.md` + `docs/design-canon/`이 정하고, 이 문서는 **무엇이
어떤 순서로 누구에게 가능한가**만 정한다.

---

## 1. 계층

```
Tenant (플랫폼)
└── 관리회사 (management_companies)
    └── 사이트 (sites)
        └── QR 배치 → QR 자산 → 차량 바인딩
```

**사이트는 관리회사 없이 존재할 수 없다.** 스키마가 이미 그렇다:
`sites.management_company_id`가 notNull이고 `(tenant_id, management_company_id)`
복합 FK다. Taptolk가 직접 관리하는 사이트도 `Taptolk 직영` 관리회사 레코드 아래에 붙는다
(`is_platform_direct` 플래그, 이름으로 판정하지 않는다).

## 2. 등록 순서 (이것이 콘솔의 척추)

| 순서 | 무엇 | 누가 | 현재 상태 |
|---|---|---|---|
| 1 | 관리회사 등록 | SUPER_ADMIN | 화면 있음. **주소검색 없음, 팝업이 좁음** |
| 2 | 사이트 등록 | SUPER_ADMIN + 해당 관리회사의 MANAGEMENT_ADMIN | `site:create` / `site:create-request` 권한은 있음 |
| 3 | QR 제작 | 위 둘이 끝난 뒤에만 | 위자드 있음. **관리회사 선택 단계가 없음** |

**QR 제작 위자드의 첫 단계는 두 단계로 갈라진다:**
`① 관리회사 선택 → ② 사이트 선택 → ③ 디자인 → ④ 수량 → ⑤ 검토·승인 → ⑥ 제작·입고`

지금 위자드는 사이트를 평면 목록으로 한 번에 보여준다. 관리회사가 늘어나면 못 쓴다.
**5단계가 아니라 6단계로 바뀐다.** (§7-A 확정 필요)

## 3. 동적 QR이 담는 것

QR 이미지에 구워지는 것은 **URL 하나**뿐이다. 관리회사·사이트 정보는 URL이 가리키는
레코드에서 나온다. 인쇄 후에는 바꿀 수 없으므로:

- canonical 호스트가 확정되어야 인쇄용 생성이 가능하다 (`PUBLIC_QR_BASE_URL`)
- QR 안에 사이트명·회사명을 **문자열로 넣지 않는다.** 사이트가 개명하면 인쇄물이 거짓이 된다
- 스캔 → 차주 정보 입력 → 서버 기록. 이 경로는 이미 `contact_sessions`로 구현되어 있다

## 4. 권한 — 관리회사별 기능 토글

**요구:** 슈퍼어드민이 관리회사마다 어떤 기능을 켤지 토글로 정한다.
특히 QR 생성 권한을 관리회사 관리자·사이트 관리자에게 줄지 여부.

현재 RBAC는 **역할 고정**이다. `roleHasPermission(role, permission)`이 정적 표를 본다.
관리회사별로 다르게 하려면 계층이 하나 더 필요하다:

```
유효 권한 = 역할 기본 권한 ∩ 그 관리회사에 켜진 기능
```

- 새 테이블 `management_company_features` (관리회사당 기능 플래그 + 감사 기록)
- `roleHasPermission`은 그대로 두고, 그 위에 `isFeatureEnabled(companyId, feature)`를 곱한다
- **토글은 권한을 넓히지 못하고 좁히기만 한다.** 역할이 못 하는 걸 토글로 켜줄 수 없다.
  넓히는 방향을 허용하면 RBAC이 두 곳에서 결정되어 감사 불가능해진다

이건 스키마 + RLS + pgTAP이 붙는 슬라이스다. (§7-B 확정 필요)

## 5. 화면 계층

| 화면 | 범위 | 접근 |
|---|---|---|
| 플랫폼 대시보드 | 전체 | SUPER_ADMIN, PLATFORM_OPERATOR |
| **관리회사 목록** | 전체 | 위 + 자기 회사만 보는 MANAGEMENT_ADMIN |
| **관리회사 상세** | 회사 1개 | 위 |
| **사이트 목록** (회사 안) | 그 회사의 사이트 | 위 + SITE_ADMIN(자기 사이트) |
| **사이트 운영 페이지** | 사이트 1개 | 위 |
| QR 제작 | 회사 › 사이트 | 기능 토글 ∩ 역할 |
| 운영 모니터링 · 리포트 | 현재 스코프 | 스코프에 따름 |
| 계정·권한 | 3계층 (§6) | SUPER_ADMIN 전체 / MANAGEMENT_ADMIN 자기 회사 / SITE_ADMIN 자기 사이트 |

**상단 "플랫폼 운영 콘솔"은 스코프 스위처다.** 전체 → 관리회사 → 사이트로 좁히면
그 아래 모든 화면(모니터링·리포트·계정)이 그 스코프를 따른다. 어드민 계정으로 특정
관리회사를 골라 그 회사 관점으로 운영·모니터링할 수 있어야 한다는 요구가 이것이다.

`ScopeSwitcher` 프리미티브는 이미 `packages/ui`에 있고, 정본 상단바에도 있다.
**현재는 표시만 하고 실제로 스코프를 좁히지 않는다.**

## 6. 계정·권한

세 계층에서 같은 화면 구조를 쓴다:

1. **전체 서비스 계정** — SUPER_ADMIN
2. **관리회사 계정** — 그 회사의 MANAGEMENT_ADMIN + 상위
3. **사이트 계정** — 그 사이트의 SITE_ADMIN + 상위

### 6.1 내 계정 (우측 상단 → 내 정보)

이름 · 연락처 · 소속 관리회사 · 소속 사이트를 보고 고칠 수 있어야 한다.

**⚠️ 주민등록번호는 이 설계에 넣지 않는다.** 개인정보보호법상 고유식별정보라
법령에 구체적 근거가 없으면 처리 자체가 금지된다(§24조의2). 관리자 계정 식별에는
필요하지 않다 — 이메일과 소속으로 충분하다. 급여·계약 등 법정 목적이 실제로 있다면
그건 별도 시스템의 문제이고, 근거 법령과 보관 기간을 먼저 확정한 뒤에 논의할 사안이다.
**이 항목은 제가 임의로 뺀 것이 아니라, 넣으면 위법 소지가 있어 보류를 제안하는 것이다.**
(§7-D)

## 7. 착수 전 사용자 확정 필요

| 표시 | 항목 | 왜 물어야 하나 |
|---|---|---|
| **A** | QR 위자드를 5단계 → **6단계**(관리회사 선택 추가)로 바꾼다 | 어제 5단계로 확정했다. 관리회사 선택을 넣으면 6단계가 된다 |
| **B** | `management_company_features` 신설 | 스키마 + RLS 슬라이스. §10 "승인 워크플로 신설"과 인접하다 |
| **C** | 고객관리 데이터 **전부 리셋** | 지금 staging에 **E2E 픽스처 테넌트 3개**가 산다. 이걸 지우면 E2E가 깨진다. 데모만 남기려면 픽스처와 데모를 분리하는 방법을 정해야 한다 (§8) |
| **D** | 주민등록번호 제외 | §6.1 |
| **E** | 사이트 등록을 MANAGEMENT_ADMIN이 **직접** 하나, **요청 후 승인**인가 | 권한 카탈로그에 `site:create`와 `site:create-request`가 **둘 다** 있다. 어느 쪽인지 정해야 한다 |

## 8. "고객관리 전부 리셋"에 대한 사실 확인

staging에는 지금 이런 게 섞여 있다:

- **E2E 픽스처**: `e2e-*` 테넌트 3개, 사이트 10개, 계정 12개. 테스트가 이걸 쓴다
- **데모 시드**: Taptolk 테넌트 아래 사이트 4개 (`7a9704b1-0d00-…`)
- 실계정 2개 (`s@i.co.kr`, `i@i.co.kr`)

**QR 위자드 현장 목록에 E2E 사이트가 나오는 이유가 이것이다.** 플랫폼 SUPER_ADMIN은
전 테넌트를 보므로 픽스처까지 다 보인다.

두 가지 방법이 있다:

1. **화면에서 거른다** — `e2e-` 테넌트를 콘솔 목록에서 제외. E2E는 그대로 산다.
   빠르고 되돌리기 쉽다
2. **staging에서 지운다** — 픽스처 데이터를 삭제. E2E는 매 실행마다 자기 픽스처를
   만들므로 원칙적으로는 가능하나, 남은 참조가 있으면 삭제가 막힌다

**권장: 1번.** E2E를 깨뜨리지 않고 화면만 깨끗해진다. (§7-C)

## 9. QR 위자드 현재 결함 (기획과 별개로 고칠 것)

스크린샷에서 확인됨:

1. 현장 목록에 E2E 픽스처가 섞여 나온다 → §8
2. 사이트를 골라도 **수량 단계에서 선택이 풀린다** — 수량 단계가 `?site=`를 안 읽는다
3. 브랜드 로고 섹션이 **또 다른 현장 드롭다운**을 띄운다 — 이미 고른 현장을 무시한다
4. 브랜드 로고 폼의 입력 글자가 디자인 시스템보다 크다
5. "Sticker Design Version" 목록은 **디자인 단계에 있을 것이 아니다** — 저장된 디자인
   버전 이력이고, 관리 화면에 속한다
6. "디자인 DRAFT 생성" 버튼 크기·톤이 정본 버튼 계약과 다르다 → §10
7. 선택된 관리 현장의 가독성이 낮다 (초록 노트 한 줄로는 부족)

## 10. 버튼 체계 재정의

정본과 `DESIGN_SYSTEM.md` §3.8이 이미 정한다: 높이 `2.5rem`, 좌우 `1.15rem`,
글자 `0.85rem`/`600`, pill, 변형 `primary`·`secondary`·`ghost`·`danger`,
크기 `default`·`compact`.

**문제는 정의가 아니라 적용이다.** 화면들이 `.tt-button`에 임의 클래스를 덧붙이거나
(`admin-approval-primary-action`, `admin-danger-action`) 폼 제출 버튼을 직접 그린다.

할 일: 콘솔의 모든 버튼을 `Button` 프리미티브 또는 `.tt-button` + 정의된 변형으로
통일하고, 화면별 버튼 클래스를 삭제한다. 어떤 버튼이 primary인지도 규칙으로 정한다 —
**한 패널에 primary는 하나.**

## 11. 제안 순서

1. §7 A~E 확정
2. **§9 위자드 결함 수정** + §10 버튼 통일 (확정 없이도 가능)
3. 관리회사 등록 화면 재구성 — 팝업 제거, 정본 상세 폼, 주소검색 연결
4. 관리회사 상세 → 사이트 목록 → 사이트 운영 페이지 계층 구현
5. 스코프 스위처를 실제로 동작시키기
6. `management_company_features` 슬라이스 (§7-B 확정 시)
7. 계정·권한 3계층 + 내 계정
8. 운영 모니터링·리포트를 위 데이터에 연결
