# Work Order — 관리자 디자인 시스템 + 지표 데이터 확장 프로그램 (2026-07-22)

> 작성: Claude(리뷰·방향·지시서). 실제 구현: Codex.
> 기준 브랜치: `codex/phase-1-foundation`. 이 문서는 여러 지시서로 나뉘는 **프로그램 로드맵**이다.
> 목표: `레퍼런스1`(관리자 대시보드 목업)의 **형식·폰트·레이아웃·밀도·색 시스템**을 전 관리자
> 화면에 일관되게 적용하고, 목업이 보여주는 **실데이터 컬럼을 정직한 스키마로 실제 구현**한다.

## 0. 배경 진단 (왜 이 프로그램이 필요한가)

`레퍼런스1`은 **완성된 가짜 데이터로 채운 고정밀 목업**이고, 현재 고객관리 화면은
**얇은 실제(합성 staging) 데이터에 정직하게 연결된 화면**이다. 격차는 두 종류다.

- **(A) 디자인 언어 격차** — 타이포/여백/타일/색/배지/페이지네이션/카드/사이드바가 목업보다 빈약.
  지금 데이터 없이 고칠 수 있다.
- **(B) 데이터·기능 격차** — 목업의 플랜 등급·차량 사용률·QR 활성화율·응답 품질·계약 만료일
  D-day·건강 스코어·미해결 건수는 **현재 백엔드에 소스가 없다.** 픽셀 복제하려면 없는 값을
  지어내야 하고, 그건 제약(고객 데이터·승인 워크플로 임의 생성 금지) 위반이다.

현재 `ManagementCompanyCatalogItem`이 노출하는 필드는 다음뿐이다:
`name, businessNumber, siteCount, contractVehicleLimit, activeQrCount, status(ACTIVE|SUSPENDED|CLOSED), createdAt, tenantId, tenantName, version`.

사용자 결정(2026-07-22): **(A) 디자인 시스템부터 만들고**, **(B) 실데이터 컬럼을 전부
스키마 확장으로 도입**한다. 화면마다 즉흥 복제하지 않고 공유 디자인 시스템을 먼저 확정한 뒤
한 화면씩 정렬한다.

## 1. 비협상 제약 (전 Phase 공통)

- `UI → Route Handler → Application Service → Domain Policy → Repository → PostgreSQL` 의존 방향 유지.
- 컴포넌트·Route Handler에 비즈니스 규칙·문구·URL·보존기간·rate limit·임계값 하드코딩 금지.
  지표 임계(만료 임박 30일, 응답 품질 버킷, 건강 스코어 룰)는 **타입 있는 도메인 정책 모듈**이 소유.
- 없는 값을 지어내 목업을 흉내내지 않는다. 데이터가 없으면 `—`/빈 상태로 정직하게 표시.
- 내부 계약 고객 식별자(tenant 이름)를 가시적 행에 노출하지 않는다. `tenant_id` 계약은 서버·RLS에서 유지.
- 중앙 RBAC + PostgreSQL RLS **모두** 통과. 보안 관련 mutation은 같은 트랜잭션에 redacted audit.
- KO/EN typed dictionary parity, SemanticHeading, immutable logo, EN "caller", QR enum·라벨 유지.
- QR 수량 `1..100` per-Batch, Production Cron 활성 `0`, canonical 단일 관리자 로그인 유지.
- 전화번호·메시지·OTP·토큰·secret 을 Git·문서·로그·스크린샷에 남기지 않는다.
- 매 웹 변경 후 `corepack pnpm validate:wcj`, 화면/Phase 완료 보고 전 `corepack pnpm verify`.
- 반응형 320/768/1280/1920, 키보드·스크린리더·명암은 별도 수동 게이트로 유지.
- Production 배포·도메인·Cron 활성·live Provider·Production Supabase·요금제·담당자 지정은
  **별도 명시 지시 없이 착수 금지.**

## 4-b. 추가 요구 (2026-07-22 사용자) — 관리사명 표시 / 관리코드 / 주소

- **목록 표시**: 관리사명은 **실제 이름**으로 표시(레퍼런스1처럼). 코드형 픽스처명("Taptolk E2E …")을
  이름 자리에 노출하지 않는다. 앱은 이미 `name`을 표시하므로 이는 **데이터(데모 시드) 문제** + 아래 코드 분리.
- **관리코드(management_code)**: `name`과 별개의 식별자 필드를 관리회사·사이트에 **신설**. 목록의 이름
  자리에 코드를 쓰지 않고, **각 상세(관리)페이지에서 관리코드를 표시·관리**한다. (스키마 추가 = P3-class)
- **상세 수정 기능**: 관리회사 상세(`[companyId]`)에서 이름·관리코드 등 **수정** 가능. (편집은 현재 목록
  행 메뉴에 존재 → 상세페이지로 정식 이전/확장.)
- **주소 + 주소검색 API**: 관리회사·사이트에 **주소 필드 신설** + 상세(관리)페이지에 **주소 검색** UI.
  한국 우편번호 검색 연동 필요. (스키마 추가 = P3-class, 클라이언트 컴포넌트 + 외부 위젯)
  - 주소는 레퍼런스 **목록 컬럼에는 없음** → 목록 테이블 설계 불변, 상세페이지 필드로만 추가.
  - API 후보: **Daum(카카오) 우편번호 서비스**(무료·키/시크릿 불필요·클라이언트 임베드, 외부 스크립트
    로드) 권장 / 행안부 Juso.go.kr 공식 API(키 발급·승인 필요·서버) / Kakao 로컬 API(키 필요·좌표).
  - 우편번호 위젯은 SMS/CAPTCHA/카카오 **메시징** Provider가 아니므로 "live Provider 착수 금지"에
    해당하지 않는다. 단 키가 필요한 옵션(Juso/Kakao)은 사용자 승인 후.
- **데모 시드 결정 필요**: staging 목록이 레퍼런스처럼 보이려면 현실적 **합성(가상) 관리사명** 데모
  시드가 필요. E2E 결정적 픽스처는 불변, 별도 데모 시드로. (DEVELOPMENT_TEST 합성 데이터 허용)

이 항목들의 스키마 슬라이스(관리코드·주소)는 P3에 포함하고, 상세페이지 수정·주소검색 UI는 P4의
관리회사/사이트 상세 정렬과 함께 구현한다.

## 4-c. 추가 요구 (2026-07-22 사용자) — 범위 전환기 / 용어 교체

### 범위 전환기 (Scope switcher) — 상단 "전체 플랫폼"
- **슈퍼어드민 전용.** 상단 스코프 칩을 드롭다운으로: **전체 플랫폼 / 특정 관리회사 / 특정 사이트**를
  선택해 그 범위의 대시보드로 전환하고 **확인·관리·수정**한다. (검색 + 관리회사>사이트 계층 목록)
- **정당성 구분(중요):** 이는 다른 사용자/역할을 가장하는 persona·role-switching(SERVICE 금지 테스트
  표면)이 **아니다.** 슈퍼어드민 본인의 플랫폼 권한을 하위 트리로 **좁히는** 것. 따라서 SERVICE 제약과
  충돌하지 않는다.
- **아키텍처/보안:** 서버가 선택 범위를 resolve → 슈퍼어드민 플랫폼 권한이 해당 하위를 포함하는지
  인가 → 범위 스코프 쿼리(tenant/company/site) → **감사에 실제 슈퍼어드민 actor + 선택 범위 기록**.
  RLS는 범위별로 계속 적용. 프론트 전환만으로 권한이 생기지 않는다.

  (전체 플랫폼 › 관리회사 › 사이트, "전체로" 리셋). 기존 `management-company-workspace-view`/
  `site-workspace-view`를 범위 드릴다운 대상으로 재사용.
- 하위 역할(관리회사/사이트 관리자)은 스코프가 고정이며 이 전환기를 노출하지 않는다.
- **분류:** P4-class(엔티티 대시보드를 범위로 스코프 + 라우팅/인가/감사). UI/UX는 프로토타입 검증 완료.
